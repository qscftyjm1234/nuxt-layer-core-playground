# 核心設計理念與依賴反轉

要「徹底榨乾」這套架構的價值，我們必須先理解它背後的核心設計理念。為什麼我們不直接寫一個普通的 Vue 專案？為什麼要大費周章弄出 `nuxt-core` 這個模組出來？

---

## 1. 為什麼選擇 Nuxt Layer 架構？

在傳統的開發模式中，當公司有第二個、第三個專案需要用到同一套按鈕、同一種分頁邏輯時，工程師通常會選擇「複製貼上」。這導致了以下災難：

- **無法同步更新**：當您發現按鈕有一個 Bug 時，您必須去十個不同的專案裡手動修補。
- **維護成本極高**：每個專案使用的 UI 框架版本可能不同，導致技術債越積越深。

本專案引入了 **Nuxt Layer** 技術。它允許我們將共用的組件、Composables、設定檔全部抽取為「核心模組」。未來的業務專案僅需加入 `extends: ['softleader-nuxt-core']`，即可繼承所有核心設定。核心模組的修復與更新將自動同步至所有繼承的業務專案。

## 2. 單一事實來源

在這個架構下，`nuxt-core` 是所有底層邏輯與設計介面的「單一事實來源」。

這意味著：

- **不重複造輪子**：如果您在業務端需要一個日期處理函式，請先到核心層的 `utils` 或 `composables` 尋找。
- **反向回饋**：如果您在業務端寫出了一個非常實用、具備高度共用價值的邏輯，請將其從業務端「拔起」，提交合併回 `nuxt-core` 之中，造福後人。

## 3. 依賴反轉 策略

這是本架構最重要的一環，也是為什麼我們強制要求一定要使用 `uiInterface` 的原因。

**依賴反轉** 的核心思想是：高層模組（業務邏輯）不應該依賴低層模組（特定 UI 框架、特定 Axios 版本），兩者都應該依賴於「抽象介面」。

### 避免底層框架高度耦合

以本專案使用的 Ant Design 為例，若業務專案直接依賴並寫滿了原生組件（如 `<a-button>` 或 `<a-table>`），若未來需要更換 UI 框架，將面臨大規模的重構成本。

### 介面隔離層：`I` 開頭的封裝組件

為解決上述問題，我們在核心層設計了 `uiInterface`。業務專案僅需呼叫 `<IButton>` 等封裝組件，無需了解底層的具體 UI 框架實作。

此設計建立了一道隔離層：

- **業務端**：僅依賴專案自定義的 `<IButton>` 介面層。
- **核心端**：在 `<IButton>` 內部處理屬性 的轉換與底層框架的對接。

若未來面臨技術框架更迭，僅需於 `nuxt-core` 中更新 `<IButton>` 的內部實作，上層業務專案的程式碼皆無需修改，大幅提升系統的穩定性與擴充彈性。
