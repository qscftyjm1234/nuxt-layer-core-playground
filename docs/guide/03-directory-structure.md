# 專案目錄結構與資料流協作機制

在進入實際開發的細節之前，身為團隊的一份子，必須先掌握整個 Monorepo 的目錄全貌，以及各個資料夾是如何「互相協力」才能將資料從後端一路渲染到畫面的。

---

## 1. 最外層結構

本專案是一個 Monorepo，核心概念在於「將多個關聯專案放在同一個 Git 儲存庫中統一管理」。

- **`apps/`**：這層放置的是「真正會跑起來的網站專案」。
  - **`playground-app/`**：供工程師在本地隨意測試、沙盒演練用的空專案。
  - **`ui-docs/`**：供設計師、PM 或是開發者查閱 UI 規格的文件站台。
- **`packages/`**：這層放置的是共用模組的集合。
  - **`nuxt-core/`**：本專案的核心模組。所有未來要提供給業務專案使用的元件、資源、工具，皆統一放置於此。

**運作概念**：`apps` 底下的所有專案，都是直接「繼承」甚至「依賴」`packages/nuxt-core/`。當在核心層加入新的工具模組後，所有 `apps` 的專案（以及後續的業務專案）皆會同步繼承並可直接調用。

---

## 2. 核心包職責解析

接下來聚焦於核心模組：`packages/nuxt-core/`。此目錄下的每一個資料夾皆具備嚴格的職責劃分：

### 畫面與表現層

- **`components/uiInterface/`**：全專案的 UI 組件介面層。僅負責視圖渲染與基本的互動效果，**嚴格禁止**在此發送 API 或處理複雜業務邏輯。
- **`layouts/`**：定義網站全域的版型結構（如側邊欄、頂部導航）。

### 業務邏輯與流程層

- **`composables/`**：全專案的邏輯控制中心。包含分頁處理、時間日期處理、彈跳視窗狀態管理、以及發送後端請求前的統一封裝 等，皆在此供視圖層呼叫。

### 資料通訊層

- **`repositories/`**：全專案的 API 請求中介層。將 API 端點依據業務領域進行分類與封裝。**嚴格禁止**視圖元件越過此層直接發送 `fetch`。此層專責處理路由邏輯與參數組合。

### 通用工具與狀態層

- **`utils/`**：全專案的通用工具模組。存放與狀態無關的純設定與函式，例如深拷貝、API 攔截器底層設定 與安全性處理 等。
- **`stores/`**：全專案的全域狀態管理。專門用於儲存跨頁面共享的資料狀態，例如使用者驗證資訊 或系統層級狀態。

---

## 3. 分層協作與資料流

各資料夾依循「單向依賴原則」進行協作。以「讀取使用者列表」的功能為例，執行流程如下：

1. **觸發操作**
   - 視圖層 (`pages/` 或 `uiInterface`) 負責捕捉使用者的操作事件（如點擊按鈕）。
2. **邏輯層處理**
   - 視圖層呼叫 `composables` 中的 `usePagination()`，傳遞獲取特定頁面資料的請求。
3. **通訊層請求**
   - `composables` 接收請求後，調用對應的 API 中介層（如 `repositories/modules/user.ts`）。
4. **API 發送**
   - Repository 負責整理參數，並透過核心封裝的 `useApi` 發送後端請求。`useApi` 將在此階段自動處理 Token 驗證與錯誤攔截。
5. **資料返回與視圖更新**
   - 資料返回至 `composables`，更新響應式變數`)。最終 `uiInterface` 接收新狀態並完成視圖重新渲染。

透過此種分層解耦的設計，當未來面臨 UI 框架替換或 API 端點變更時，僅需修改對應職責的資料夾，大幅降低跨層級的影響範圍，確保專案的可維護性。
