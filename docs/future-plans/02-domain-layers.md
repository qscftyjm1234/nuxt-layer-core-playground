# 擴充藍圖：業務模組樂高化

隨著核心包涵蓋的功能越發廣泛，將所有功能打包在一起會導致某些專案引入了不需要的套件（例如形象官網不需要金流功能）。
未來的架構將朝向**微模組化** 發展。

## 1. 概念與價值

核心包將拆分為一個基礎層（Base Layer）以及多個可選的**業務領域層**。
新專案就像組裝樂高，基礎元件是必備的底座，而金流、會員認證等功能則是依照需求加上去的積木。

## 2. 模組拆分架構

### Base Layer (現有核心)

處理所有專案共用的基礎設施，包含：

- 共用 UI 介面（按鈕、彈窗、表格）。
- 底層 API 攔截器與錯誤處理。
- 基礎的通用工具 與全域設定。

### Domain Layers (未來擴充模組範例)

- `@softleader/payment-layer`：專注處理第三方支付串接、信用卡防呆組件、結帳購物車邏輯。
- `@softleader/auth-layer`：處理複雜的角色權限管控、SSO 登入、Token 刷新機制。

## 3. 資料結構與型別的隔離策略

當模組被拆分後，確保**所有專案對資料結構的認知一致**是非常重要的：

1. **核心型別**：
   - 對於全站通用的資料結構（如 `User`, `ApiResponse`, `Pagination`），這類最基礎的介面定義（Interfaces）應留在 Base Layer，供百搭使用。
2. **領域型別**：
   - 領域層特定的資料結構（例如：`PaymentTransaction`, `CreditCardInfo`）必須封裝在其專屬的 Domain Layer 內部。
   - **優點**：如果 A 專案沒有引入 `payment-layer`，開發人員也不會在使用 TypeScript 提示時，被不相關的金流型別干擾。
3. **介面擴充**：
   - 若某些資料結構需要聯動（例如：基本 User 資訊與金流狀態），我們將善用 TypeScript 的泛型與介面合併機制，確保核心模組與業務模組之間保持鬆耦合。

## 4. 未來影響

業務模組的拆分，能幫助松凌在承接各種規模專案時，保持每個專案的依賴最乾淨、體積最小，同時資料結構與型別定義也能精準對應實際開發的需求。
