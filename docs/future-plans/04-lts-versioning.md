# 擴充藍圖：多版本平行維護

作為公司的開發核心，專案的改版一定會影響到底下的業務專案。為了確保現有系統的穩定性，並兼顧新技術的引進，我們定義了企業級的 **LTS** 多版本維護策略。

## 1. 概念與價值

當核心包需要進行破壞性更新（Breaking Changes），例如從 Vue 3 升級到某個不相容的底層庫，版本號將會從 v3 一躍成為 v4。
在這個時刻，我們不會強迫所有專案立即升級，而是採取「版本平行分流」的維護機制。

## 2. 實作架構規劃

### 維護分支 的切分

當 v4 成為主線開發（Main Branch / `latest` tag）時：

1. **建立專屬分支**：我們將針對前一個主要版本（例如 v3）切出獨立的維護分支（例如：`v3-maintenance`）。
2. **NPM 發布通道**：
   - 新版本 v4 發布至 NPM 的 `latest` 標籤：`npm install @softleader/nuxt-core@latest`
   - 舊穩定版 v3 透過專屬標籤發布：`npm install @softleader/nuxt-core@v3-lts`

### 雙修復機制

當發現了核心組件的安全性漏洞或重大 Bug 時：

- 工程師首先在主線 進行修復。
- 將該修復 Commit 透過 `cherry-pick`（或者 Backport 工具）反向移植回 `v3-maintenance` 分支。
- 這樣停留在舊版的專案，依然可以透過更新小號次（例如 v3.1.2 升級至 v3.1.3）獲得緊急修復，而不需承擔直接升 v4 的風險破壞。

## 3. 對公司的未來影響

1. **資源調配**：新承接的專案或時程寬裕的專案可以直接使用前沿的 v4 版本享受新功能。而進入維護期、沒預算改寫的老專案，可以安穩待在 v3 LTS，確保公司有足夠的緩衝期應對技術債。
2. **發布信心**：團隊在開發破壞性新功能時不再綁手綁腳，因為我們知道舊有的生態圈已被穩固的 LTS 機制保護著。
